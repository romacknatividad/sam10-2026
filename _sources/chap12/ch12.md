# High Availability, Scalability, and Reliability Engineering

## Learning Objectives
- Define **reliability, scalability, fault tolerance, elasticity**.
- Apply **fault tolerance** with redundancy and circuit breakers.
- Configure **Auto Scaling**.
- Build **multi-AZ** systems.
- Use **health checks**.

---

## Availability & Reliability

**Reliability** = the system performs its function *correctly and continuously* under stated
conditions for a period of time. Closely related: **availability** = uptime %.

$$
\text{Availability} \approx \frac{\text{MTBF}}{\text{MTBF} + \text{MTTR}} \times 100\%
$$

- **MTBF** = Mean Time Between Failures; **MTTR** = Mean Time To Repair/Recover.
- **Five-nines (99.999%)** allows ~5 minutes of downtime **per year**.

Raise availability by *increasing MTBF* (fewer failures) **or shrinking MTTR** (faster recovery).

---

## Scalability

**Scalability** = handle more load by adding capacity.

| Kind | What | Trade-off |
| --- | --- | --- |
| **Vertical (scale-up)** | add vCPU/RAM to one node | limited, easy |
| **Horizontal (scale-out)** | add more nodes | no single-node ceiling |

**Statelessness** is the biggest enabler of scale-out: each request is independent and any
node can serve it.

$$
L = \lambda \cdot W \quad \text{(Little's Law)}
$$

Concurrency `L` = arrival rate `λ` × time in system `W`. So **reducing latency multiplies capacity**.

---

## Fault Tolerance

**Fault tolerance** = keep working *correctly* when parts fail. Assume failure is the norm.

Patterns (the "four T's" of resilient systems):
- **Redundancy** (multiple AZs/regions, replicated data).
- **Transient retry** with **exponential backoff + jitter** (avoid thundering herd).
- **Timeouts** (fail fast instead of holding resources forever).
- **Circuit breakers** (stop sending to a failing dependency until cooldown).

:::note
Retry with backoff+jitter &rarr; circuit breaker opens &rarr; fail fast, isolate the blast radius
:::

---

## Elasticity

**Elasticity** is *automatic* capacity adjustment to match *fluctuating* demand. It is
scalability + automation + a cost constraint. **Auto Scaling** is the AWS mechanism.

---

## Auto Scaling

An **Auto Scaling group (ASG)** keeps the number and health of instances correct across AZs.

| Piece | Role |
| --- | --- |
| **Launch Template** | what to launch (AMI, type, SGs, user data) |
| **ASG** | pool across AZs with min/desired/max |
| **Scaling policy** | when how to change count |

Policy types:
- **Target tracking**: keep metric (e.g., CPU 50%) — simplest.
- **Step scaling**: tiers of response.
- **Scheduled**: predictable daily/weekly load.

**Health checks**: EC2 status checks OR **ELB health checks** — unhealthy targets are
deregistered and replaced (self-healing).

:::note
Start with a conservative min, sensible desired, high max; target-track CPU at ~50-60%; review cooldowns.
:::

---

## Multi-AZ

**Multi-AZ** = redundant copies in **separate AZs, same Region**.

| Service | Multi-AZ means |
| --- | --- |
| **RDS** | synchronous standby AZ → automatic failover (HA; *not* read scaling) |
| **EFS** | replicated across AZs automatically |
| **ALB + ASG** | instances spread across AZs; cross-zone balancing |

**Multi-AZ ≠ Multi-Region**: AZ gives *high availability*; Regions give *disaster recovery*
(Ch 13).

---

## Health Checks

A probe that decides whether a target is *healthy*.

| Kind | Where | Typical target |
| --- | --- | --- |
| **ELB health check** | target group | `HTTP:80/health` |
| **EC2 status check** | instance | CPU/network/IO |
| **Route 53 health check** | DNS failover | external endpoint |
| **Custom** | ASG / NLB | app-defined OK |

Settings: **interval**, **timeout**, **healthy threshold**, **unhealthy threshold**. The LB
must take at least one *unhealthy* interval's worth of failures before removing a target — keep
thresholds tight but not flappy.

## Checkpoint

```{dropdown} Q1. If MTTR halves but MTBF is unchanged, what happens to availability?
**Answer.** Availability **rises**: the denominator shrinks while MTBF stays the same.
```
```{dropdown} Q2. Why does statelessness make an app far easier to scale out?
**Answer.** Any request can go to any node, so requests can be load-balanced evenly without
synchronizing session state.
```
```{dropdown} Q3. Give two resilience patterns besides replication.
**Answer.** Exponential backoff+jitter retries, and circuit breakers (fail-fast); also timeouts.
```
```{dropdown} Q4. Difference between *scaling* and *elasticity*?
**Answer.** Scaling = adding/removing capacity (manual or automatic). Elasticity = **automatic**
scaling in response to demand **within cost bounds**.
```
```{dropdown} Q5. How does ELB + ASG achieve self-healing?
**Answer.** ELB health checks detect a sick target → ASG replaces the unhealthy instance via
the launch template → fresh healthy target takes traffic.
```

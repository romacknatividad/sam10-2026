## Systems and Systems Theory

A **system** is a set of interdependent parts that transform inputs into outputs with
feedback from the environment. An **open system** exchanges matter/energy/information
with its surroundings; a closed one does not (data centers are open systems).

| Concept | Meaning |
| --- | --- |
| **Emergence** | whole > sum of parts |
| **Hierarchy** | subsystems nested in larger systems |
| **Homeostasis** | stable equilibrium despite change |
| **Feedback** | positive amplifies; negative *stabilizes* |
| **Entropy** | disorder rises unless energy added |

:::{note}
Monitoring is the system's **negative-feedback** mechanism: measure → compare to target → act.
:::

## Operating System Fundamentals

The **OS** manages hardware and offers common services. Its core functions:

| Function | What it does |
| --- | --- |
| Process mgmt | create/schedule/terminate processes, allocate CPU |
| Memory mgmt | allocate RAM, virtual memory, swapping |
| File system | organize files/dirs, store/retrieve data |
| I/O mgmt | devices, drivers, interrupts, buffering |
| Security | authN/authZ, permissions, audit |
| Networking | TCP/IP stack, sockets |
| User interface | shell (CLI) or GUI |

### Kernel vs. user space
The **kernel** runs in privileged *kernel mode* (ring 0); apps run in *user mode* (ring 3) and
cross the boundary only via **system calls** (`open`, `read`, `socket`). This isolation stops a
crashing program from taking the OS down.

```
        + Application(s)  (user mode)
        + Libraries / shell
        ----- syscall boundary -----
        + Kernel (scheduler, VFS, net, drivers)  (kernel mode)
        + Hardware (CPU, RAM, disk, NIC)
```
A sysadmin's mental model: think in **processes**, **files**, **permissions**, and
**listening services**.

## Client-Server Architecture

**Client–server**: a client *requests* a service; a server *provides* it over a network.

```{figure} ../diagrams/clientserver.svg
:width: 80%
:align: center

Three clients send requests and receive responses from a shared server.
```
Centralized control, easier security, and independent scaling are the trade-offs against a
single-server bottleneck (which we solve with *load balancing* in Chapter 9).

### Three-tier separation
Presentation → Application (business logic) → Data. Each lives on separate hosts → separate
failure domains (see Chapter 9).

## Roles of a Systems Administrator

The **systems administrator** installs, configures, maintains, monitors, and supports systems
and networks.

**Core responsibilities**
- Install/upgrade OS & software; **patch management** (Ch 13/14).
- Manage **users, groups, permissions**.
- **Monitor** health/perf; **capacity planning**.
- **Backup & recovery**.
- **Automate** (scripts / IaC) and **document** (runbooks).
- Keep a **supportable 24/7** posture.

**Skills**: shell scripting, OS internals, networking, cloud/DevOps, documentation.

:::{tip}
Always act with **least privilege**; prefer RBAC and short-lived credentials over permanent
root access.
:::

## AWS Global Infrastructure

AWS is a hierarchy of Regions, Availability Zones (AZs), and Edge Locations.

```{figure} ../diagrams/regions_az.svg
:width: 80%
:align: center

Regions contain multiple AZs (isolated); Edge locations are for content/DNS delivery.
```

| Unit | Scope | Purpose |
| --- | --- | --- |
| **Region** | geographic area | isolated, e.g., us-east-1 |
| **AZ** | 2–3 isolated DCs in a region | fault domains |
| **Edge Location** | worldwide points | CDN, DNS, Lambda@Edge |

Multi-AZ = high availability within a Region; Regions = disaster recovery (Ch 13).

## AWS Shared Responsibility Model

Security is **shared**: AWS secures the **cloud**, the customer secures **in** the cloud.

```{figure} ../diagrams/shared_resp.svg
:width: 80%
:align: center

AWS owns physical infrastructure; the customer owns data, identity, OS, network config.
```

| Layer | Responsible party | Your controls |
| --- | --- | --- |
| Physical/host/hypervisor | **AWS** | — |
| Network config, OS, apps, data, IAM | **Customer** | IAM, SG, OS, encryption |
| Patching (some shared) | shared | SSM Patch Manager, app-level |

## Checkpoint

```{dropdown} Q1. Which layer does the OS kernel run in, and how do apps enter it?
**Answer.** Kernel mode (ring 0); apps enter via system calls such as `open`, `read`, `socket`.
```
```{dropdown} Q2. Name the five NIST cloud computing characteristics.
**Answer.** On-demand self-service, broad network access, resource pooling, rapid elasticity, measured service.
```
```{dropdown} Q3. What separates an AWS Region from an Availability Zone?
**Answer.** A **Region** is a geographic area; an **AZ** is one or more isolated data centers
within it; AZ failure ≠ Region failure.
```
```{dropdown} Q4. Under the Shared Responsibility Model, who patches an EC2 *guest OS*?
**Answer.** The **customer** (AWS patches the hypervisor/host). IaaS means you own the OS.
```
```{dropdown} Q5. What is the Feedback Law's relevance to sysadmin?
**Answer.** Systems drift (entropy); monitoring is negative feedback that detects drift and
triggers action to restore the target state.
```
